## Epics

### 12 — AI Creations in the Content Library, and Media Library request state
Slug: `media-library-ai-creations-and-request-state`

**Rewritten after PO review.** The first draft framed this as async AI generation job tracking; that was wrong. Verified cause: the media list API has no AI filter at all. The frontend sends `is_ai_generated`, the controller never maps it and the repository's list query applies only folder, search, mime type, sort, usage and archived. So AI Creations asks for the whole library, filters it in the browser, and recursively re-requests pages until it fills, bounded only by a five-page cap and an empty-streak guard, both added after the loop previously "fetched empty pages forever" per its own comments. All uploads is hit identically. Separately the sidebar count tallies AI-flagged media rows only, so it excludes AI Posts (a different collection entirely), and the pills overlap because AI Studio currently returns all AI media including clips.

1. `[BE]` Filter media by AI origin on the library API instead of returning everything
2. `[BE]` Make the AI Creations count reflect all three categories
3. `[FE]` Consume the AI-filtered media API and remove the page-refetch loop
4. `[FE]` Fix Media Library request and loading state so the loader leads the empty state
5. `[Design]` AI Creations pills, counts and empty states

Three decisions are needed before the backend story starts: what the count means, whether AI Studio should exclude clips, and how existing AI media is classified if an origin field is added.

### 13 — Best Time to Post across the public developer surfaces
Slug: `public-api-best-time-to-post`

Best Time to Post is computed inside the internal analytics stack and consumed only by the Composer scheduling UI. There is no best-time route anywhere in the public API, so a customer automating publishing can schedule posts but cannot ask us when to schedule them, and ends up rebuilding the recommendation from raw analytics and getting a different answer than our own UI shows. This epic exposes it per connected account with an explicit contract, then propagates it to every developer surface.

1. `[BE]` Expose Best Time to Post per connected account in the public API
2. `[BE]` Document Best Time to Post in the OpenAPI spec and API guide
3. `[CLI]` Add best posting times to the CLI and the agent skill
4. `[MCP]` Add a best-time-to-post tool to the MCP server
5. `[Claude Extension]` Surface best posting times in the Claude extension
6. `[GPT App]` Add a best-time-to-post action to the GPT app schema
7. `[Zapier]` Add a best-time-to-post search step
8. `[Make]` Add a best-time-to-post module
9. `[n8n]` Add a best-time-to-post operation
10. `[ClawHub]` Refresh the published ContentStudio skill with the best-time commands

Two decisions are called out in the research: which networks are supported (best-time queries exist for Facebook, Instagram and LinkedIn only) and whether the public contract exposes a raw score or a documented confidence.

### 18 — Manage Inbox auto-reply help docs from Brand Knowledge
Slug: `brand-knowledge-inbox-autoreply-docs`

We ask users for their documents twice. Brand Knowledge already accepts documents as a source type; Inbox auto-replies has a completely separate document store with its own upload, quota, management modal, delete-confirmation flow and per-rule picker. A user who has set up Brand Knowledge with their policies and FAQs opens the auto-reply form and is told "No help documents uploaded yet". This epic makes Brand Knowledge the single store with a per-document opt-in for auto-replies, defaulting off, because an internal pricing sheet should not automatically become something the AI quotes to a customer.

1. `[BE]` Add an Inbox auto-reply opt-in to Brand Knowledge documents and serve them to the auto-reply engine
2. `[FE]` Add the Inbox auto-reply control to the Brand Knowledge Source Materials tab
3. `[FE]` Point the auto-reply help-docs selector at Brand Knowledge documents
4. `[Design]` Brand Knowledge document row with the Inbox auto-reply control

Three decisions must be settled before the backend story starts: migration of existing Inbox help docs, whether quotas unify, and storage accounting.

### 19 — Standardize chart UI across Analytics
Slug: `analytics-chart-ui-standardization`

Thirty-six chart components share an engine and nothing else. `useEcharts()` owns the instance lifecycle and contributes nothing visual, so legend, axes, grid inset, palette, value formatting and the empty, loading and error states are each built per component. The same chart exists as separate per-network files (`AudienceGrowthChart`, `HashtagsChart`, `PublishingBehaviourChart`, `DualChartComponent` all recur), so fixing one network's copy does not fix the others. Report section headers also carry a fixed gradient rather than theme tokens.

1. `[Design]` Define the Analytics chart standard
2. `[FE]` Build the shared chart option layer and adopt it in the per-network charts
3. `[FE]` Adopt the shared chart layer in the ads, competitor and overview charts

Sequence after **[FE] Migrate the analytics module to TypeScript & TanStack Query** if that lands in the same period, so chart loading and error states come from query state rather than being hand-rolled and then redone.

### 20 — Analytics metric consistency
Slug: `analytics-metrics-consistency-audit`

**Scoped down.** The request had four parts; two are already authored and were dropped rather than duplicated:

- *Finalize report widget selection* is **[Full Stack] Let users pick which sections to include in analytics reports** in `analytics-report-sections-and-overview-cards`.
- *Standardize Top Posts and Account Insights counts* is **[Full Stack] Cap overview top posts and account insights at five and hide metrics a platform does not report**, with **[Full Stack] Add the Top Posts sort dropdown + Least Posts to Facebook, Instagram, LinkedIn & TikTok analytics** covering the related gap.

What remains is genuinely uncovered: the same metric is named, derived and formatted differently depending on which of eight surfaces you look at, and a number on screen does not always match the number in the PDF a user sends their client. `analytics-api-consistency` standardizes the transport layer, not the display layer.

1. `[Full Stack]` Audit Analytics metrics and publish one canonical metric definition set
2. `[Full Stack]` Reconcile metric naming, derivation and formatting across Analytics surfaces

The audit is deliberately separate: fixing before agreeing what each metric means just produces a different set of inconsistencies. It also answers the outstanding count question (`TOP_POSTS_LIMIT = 5` on Facebook and Instagram overview, `10` on YouTube and on label-and-campaign reports).

### 26, 27, 28 — Inbox network research: Telegram, Bluesky and Threads
Slug: `inbox-network-research-telegram-bluesky-threads`

Three networks we publish to with no presence in Social Inbox. None resembles the networks the inbox was built around, so research first is genuinely right here. One story per network.

1. `[Research]` Telegram Inbox feasibility and recommended scope
2. `[Research]` Bluesky comments and replies in Inbox: feasibility and recommended scope
3. `[Research]` Threads comments and replies in Inbox: feasibility and recommended scope

**Telegram is already half answered by our own code.** `TelegramConnector.php` uses the Bot API with a bot token, and its `validateToken()` already stores `can_join_groups` and `can_read_all_group_messages`. That second flag is Telegram's privacy-mode indicator and largely decides whether a Telegram inbox can see group conversation at all. Our existing `docs/features/telegram-integration/01-research.md` additionally records that a bot cannot message a user who has not messaged it first, and that Zoho Social shipped a Telegram inbox in 2024. So that story's real question is what the resulting inbox can actually do, not whether it is possible.

Remaining deltas: the website says Monthly/Yearly with "Save up to 34%" while the app computes a per-plan saving; the website badges Agency Unlimited "Best Value" while the app has an `isPopular` flag; the website names seven add-ons under one heading. Two defects found in passing: the API plan and recommended-plan card borders are hardcoded hex (`#16a34a`, `#007bff`), so neither themes for white-label, and the API plan is hidden entirely on white-label domains so the layout must hold at three columns.
- **16** — RSS and Bulk CSV both use the shared `StepIndicator`. Evergreen hand-rolls its own with a different hardcoded hex per step (`#7272FF`, `#4CCE88`, `#FF9472`), which also means it cannot follow a white-label brand colour. Step state, visibility, validation and exit confirmation are each done three ways.
- **21** — The shared scaffold already exists from **[FE] Rework post previews in Composer and Planner for platform fidelity and consistent sizing**, and is consumed only by `planner_v2` and composer. Inbox and Analytics hand-roll their own; one Analytics preview detects video by checking a URL for substrings. The complication is that Composer and Planner preview *unpublished* posts while Inbox and Analytics show *published* ones with real engagement counts, so this needs an adapter and a real-counts engagement bar, not drop-in reuse. That is why the Inbox story is first.
- **22** — Authored as **one story, as requested**. A three-way split is recommended inside the doc for the PO to accept or reject: the two UI fixes have no commercial consequence, while the Blog and Website Mentions part is a billing implementation gated on pricing decisions, so bundled, the quick fixes cannot ship until those decisions are made. Web mentions are already fully built and ungated (`{ id: 'web', label: 'Blogs & sites' }` is in the platform picker, mention rendering handles it, the crawler exists); only the commercial side is unfinished.
- **25** — Root cause is one message serving two causes. `genericUploadsAllowed` is false either because the model accepts no reference images at all (`allowReferences: false`, today `kling-video-v2.5-turbo-pro` and `flux-3`) or because a frame is set on a model that cannot combine them, and both produce "Start/end frames and reference images can't be used together". `frameReferenceConflict` returns a conflict without checking `hasFrames` at all. The same collapse appears in three places.
