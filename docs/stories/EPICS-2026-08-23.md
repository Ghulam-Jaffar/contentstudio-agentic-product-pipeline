## Headline findings from research

1. **Notifications** are produced through at least five independent pipelines. The main in-app and email path runs through a plain Redis list drained by one command with a ten-branch router, so there is no retry, no dead-letter path and no delivery visibility. Mobile push has three separate code paths, two device registries, and serves exactly one product flow. Approval notifications never reach mobile at all, and the Flutter app currently recognises a single push intent.
2. **Service authorization.** The analytics service validates a token's signature and then ignores the authenticated identity in every handler except one, while reading the requested workspace from the request. The inbox service has already built the membership check that closes this, but it is behind a rollout flag, applies only to requests that name a workspace, and checks membership rather than role. Its own module docstring names the issue as an IDOR.
3. **Internal networking.** The AI agents platform, the micro-links service and the optimal-times service are all called over public hostnames despite being internal-only. Gotenberg is already addressed internally and proves the pattern. The analytics and inbox services must keep a public entry point for the browser, so this epic and epic 2 overlap by design.
4. **Platform identifier.** Six platforms still identify accounts by a legacy per-platform key, one is configured with two different keys, and two use their name. Roughly 2,200 legacy-key occurrences remain across the three codebases against roughly 890 platform-identifier ones. Separately, every per-platform account model reads the same single collection, so fetching a workspace's accounts costs one query per network.
5. **MCP.** Tools take the API token as a tool parameter, so the credential travels through the model's context. No authorization server exists. That is the blocker for both connector directories, independent of tool quality.
6. **Usage visibility.** AI credits are running counters on the workspace document, clamped to the plan limit and reset periodically, so no history, no per-event detail and no cost data exist. The AI platform already computes provider cost and retail price and sends both on every usage event, and the main product discards both. Server-side Usermaven reporting does exist, but all six X events fire only on blocks, spending limits, top-ups and auto-recharge, never on a successful spend, so product analytics can show when a customer was stopped and never what they consumed. The X wallet ledger is the one proper per-event record and is the pattern to follow, though it captures what we charged and not what X charged us.

## Cross-epic dependencies

- Epic 2 and epic 3 overlap on the browser-facing services. One of epic 2's candidate approaches is a single authorization point in front of them, which is also where epic 3's routing lands.
- Epic 5 takes the "which MCP server do we keep" decision from the existing `ai-surfaces-architecture` epic, and reuses epic 2's conclusion on constraining a caller to the user's real permissions.
- Epic 6 builds on the existing `x-pay-per-use-credits` and `x-analytics-metering` work and should follow the retention approach from `analytics-observability-and-data-retention`. Its two stories share one record shape and one internal-admin ingestion path, so whichever ships first establishes both.
- Epic 1 sequences alongside `replace-pusher-with-centrifugo` and the existing analytics and inbox webhook event work.

## Open questions for the PO

1. **Epic 6:** no internal admin surface exists in the mounted repositories, though the analytics service accepts an internal-admin token, so one exists somewhere. Where it lives, who owns it and how it ingests data is an acceptance criterion on both stories and must be resolved rather than deferred.
2. **Epic 6:** provider cost and margin are deliberately not sent to Usermaven, on the grounds that unit economics should not go to a third-party analytics processor. Override if that is not the intent.
3. **Epic 5:** whether white-label customers get their own connector listing or are excluded is a product decision, flagged as an acceptance criterion rather than assumed.
4. **Epic 4:** legacy identifier fields stay in stored data. Whether they are eventually removed is a separate migration decision outside the epic.
