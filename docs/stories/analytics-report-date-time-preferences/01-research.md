# Analytics Reports: Respect Date, Time and Timezone Preferences · Research

## Current State

Analytics report PDFs are generated by the Go service (`contentstudio-social-analytics-go`). Dates on those PDFs are rendered with **hardcoded layouts** that ignore the user's saved preferences.

### What the user can set today

Settings → Profile stores three relevant preferences:

| Preference | Where it lives | Values |
|---|---|---|
| Date format | `user.preferences.date_format` | `MM/DD/YY`, `MMM DD, YYYY`, `YYYY MMM DD`, `DD MMM YYYY` — options defined in `contentstudio-frontend/src/modules/setting/composables/useProfilePage.ts:57-73` |
| Time format | `user.preferences.time_format` | `12h`, `24h` — read at `useProfilePage.ts:211` |
| Timezone | Workspace-level timezone | IANA zone, e.g. `America/New_York` |

The web app honours all three. `contentstudio-frontend/src/composables/useDateTime.ts:31` falls back to `MMM DD, YYYY`, and `CstInputFields.vue:159`, `RecentPosts.vue:51` and the planner all read `profile.date_format`.

The PHP backend honours the date format too: `UsersRepository::getDateFormat()` (`contentstudio-backend/app/Repository/Account/UsersRepository.php:1105-1109`) feeds `ReportsHelper` in both `app/Libraries/Analytics/ReportsHelper.php:1050-1065` and `app/Services/Analytics/ReportsHelper.php:383-388`, with a `j M Y` fallback.

### What the Go report generator does instead

The report definition already carries `Language` and `Timezone` (`contentstudio-social-analytics-go/src/models/reports/definition.go:126-127`), and `Timezone` is threaded through to every platform adapter for data bucketing. **There is no date-format or time-format field on the definition at all** — grepping `date_format` across the Go source returns nothing.

Dates are formatted with fixed Go layouts:

| Location | Layout | Problem |
|---|---|---|
| `src/services/reports/reportsvc/service.go:309` — cover "generated at" | `Jan 02, 2006 03:04 PM` | Fixed date layout, forced 12-hour clock, and uses `s.now()` which is **server time, not the workspace timezone** |
| `src/services/reports/reportsvc/service.go:403-410` — `fmtCoverDate`, cover date-range pill | `Jan 02, 2006` | Fixed layout |
| `src/services/reports/adapters/competitor/facebook.go:504-508` — chart labels | `Jan 2` | Fixed layout |
| `src/services/reports/adapters/campaign_label/adapter.go:925-932` — day keys | `2006-01-02` | Internal key, likely fine, but should be confirmed it never reaches the page |

### The one localization that does exist

`src/services/reports/localization/dates.go` swaps English month abbreviations for the report language (`de`, `es`, `fr`, `it`, `pl`, `el`, `zh`). Its own comment states the limitation plainly:

> "The report formats cover dates as 'Jan 02, 2006 …', so localizing the month token is enough to make the date read in-language (full per-locale date reordering is a later polish)."

So a French report reads `janv. 02, 2026` — the month is translated but the ordering stays American. This ticket is that "later polish", driven by the user's explicit preference rather than by locale.

### Net effect for the user

A user who has set `DD MMM YYYY` and a 24-hour clock sees their preference honoured everywhere in the web app, then downloads an analytics report PDF and gets `Jan 02, 2026` and `03:04 PM`. The "generated on" stamp is also in server time, so it can show the wrong day near midnight for users far from the server's zone.

---

## What Needs to Change

- Carry the user's date format and time format through to the Go report generator, alongside the `Language` and `Timezone` fields the definition already has.
- Replace the hardcoded layouts on the cover date-range pill and the "generated on" stamp.
- Render the "generated on" stamp in the workspace timezone rather than server time.
- Apply the same treatment to any date that appears on a chart axis or in a table within the report body.
- Keep the existing month-name translation working on top of the chosen format.
- Define the fallback when a user has no preference saved, matching the web app's `MMM DD, YYYY` default so reports and screen agree.

## Scope Notes

- Applies to both on-demand downloads and scheduled report emails, since both run through the same Go generator.
- The shareable report link renders the same PDF, so it is covered by the same change.
- Timezone is already on the definition and already used for data bucketing. Only the presentation timestamps need fixing, not the underlying data windows. Worth stating clearly in the ticket so nobody re-buckets the data.
- `contentstudio-social-analytics-go/src/services/reports/adapters/bluesky/adapter.go:447` carries a deliberate note that hour buckets are **not** locale-formatted because they are buckets in the workspace timezone, not instants. That decision should stand.

## Mobile Context

Not impacted. Report PDFs are generated server-side and are not composed in the app.
